1. FRONTEND FILES (frontend/)
================================================================================
The frontend is a single-page React 19 application built with TypeScript, Vite,
and Tailwind CSS. It communicates with the FastAPI backend for RAG queries and
directly with Supabase for authentication, patient records, and audit logging.

2. BACKEND FILES (backend/)
================================================================================
The backend is a high-performance Python 3.11 FastAPI service. It handles PDF
text extraction, semantic chunking, dense vector embeddings generation (using
BAAI/bge-small-en-v1.5 running locally), similarity search over Supabase pgvector,
and high-throughput LLM synthesis via Groq.

  * Use: Installs FastAPI, Uvicorn, SentenceTransformers, Pydantic, Supabase Python SDK,

- backend/.env

--------------------------------------------------------------------------------
2.3. Pydantic Data Schemas (backend/app/schemas.py)
--------------------------------------------------------------------------------

- backend/app/schemas.py
  * Why Created: Defines strongly-typed request and response schemas using Pydantic.
  * Use:
    - `AskRequest`: Validates incoming query string, optional patient_id, and category filter.
    - `EvidenceSource`: Defines structure for retrieved guideline citations (title, page, chunk).
    - `AskResponse`: Validates returned recommendation, confidence, evidence list, and metadata.
    - `HealthResponse`: Models health check payload (status, groq_configured, supabase_connected).

--------------------------------------------------------------------------------
2.4. Data Ingestion Pipeline (backend/app/ingestion/)
--------------------------------------------------------------------------------

- backend/app/ingestion/__init__.py
  * Why Created: Marks `ingestion` as an importable Python subpackage.
  * Use: Enables clean imports of ingestion pipeline components.

- backend/app/ingestion/pdf_loader.py
  * Why Created: Extracts raw text and page numbers from official clinical PDF guidelines.
  * Use: Downloads or reads local PDF documents (e.g., CDC Opioid Guidelines) using `pypdf`,
    strips extraneous whitespace, and returns structured page-by-page text objects.

- backend/app/ingestion/chunker.py
  * Why Created: Breaks continuous guideline text into semantically coherent chunks.
  * Use: Implements recursive token/character chunking (~500 tokens with 50-token overlap)
    while preserving page numbers and section headers to ensure accurate point-of-care citations.

- backend/app/ingestion/index_guidelines.py
  * Why Created: Command-line runner that executes the full end-to-end ingestion pipeline.
  * Use:
    1. Loads guideline documents.
    2. Splits them into chunks with `chunker.py`.
    3. Generates 384-dimensional embeddings using `embeddings.py`.
    4. Upserts all chunks and vectors into Supabase's `guideline_chunks` table.

--------------------------------------------------------------------------------
2.5. Core RAG Services (backend/app/services/)
--------------------------------------------------------------------------------

- backend/app/services/__init__.py
  * Why Created: Marks `services` as an importable Python subpackage.
  * Use: Exposes core business logic modules to routers and test suites.

- backend/app/services/query_router.py
  * Why Created: Fast pre-retrieval query classifier that filters incoming requests.
  * Use: Uses regex patterns and an extensive clinical lexicon to classify queries into:
    - `greeting`: Returns polite greeting without expensive vector lookup.
    - `out_of_scope`: Gracefully declines non-medical queries (coding, trivia, cooking).
    - `unclear`: Requests clarification for vague queries.
    - `healthcare`: Routes valid clinical questions into the semantic retrieval pipeline.

- backend/app/services/embeddings.py
  * Why Created: Singleton wrapper around local SentenceTransformers model.
  * Use: Loads `BAAI/bge-small-en-v1.5` onto CPU/GPU in a thread-safe singleton.
    Encodes queries and document text into 384-dimensional dense normalized vectors.

- backend/app/services/retrieval.py
  * Why Created: Interacts with Supabase pgvector and PostgreSQL RPC functions.
  * Use:
    1. Calls Supabase RPC `match_guideline_chunks` with query embedding, threshold (0.40),
       and match count (top 5).
    2. Fetches patient context (conditions, medications, allergies) from the `patients` table.

- backend/app/services/groq_service.py
  * Why Created: High-throughput LLM synthesis service powered by Groq API.
  * Use: Formulates strict, hallucination-free medical prompts combining retrieved
    guideline evidence and patient context. Queries `qwen/qwen3.8-27b` with automatic
    fallback models if rate limits or outages occur.

- backend/app/services/rag.py
  * Why Created: Master orchestrator connecting all backend services.
  * Use:
    1. Routes query through `query_router.py`.
    2. If clinical, embeds query via `embeddings.py`.
    3. Retrieves top chunks and patient data via `retrieval.py`.
    4. Synthesizes evidence-grounded answer via `groq_service.py`.
    5. Formats and returns final `AskResponse` with citations.

================================================================================
3. DATABASE FILES (database/)
================================================================================
The database tier uses Supabase (PostgreSQL 15+) with the `pgvector` extension.
It stores patient records, guideline catalogs, vector embeddings with cosine
distance indexing, and the clinical decision audit trail.

--------------------------------------------------------------------------------
3.1. SQL Schema Migrations (database/migrations/)
--------------------------------------------------------------------------------

- database/migrations/001_patients.sql
  * Why Created: Defines the patient demographics and medical profile schema.
  * Use: Creates `patients` table (UUID, code, name, age, gender, chronic conditions,
    medications, allergies, vitals, timestamps). Implements automatic patient code
    generation trigger (`PAT-0001`) and Row Level Security (RLS) policies.

- database/migrations/002_guidelines.sql
  * Why Created: Schema for the authoritative clinical guidelines catalog.
  * Use: Creates `guidelines` table (id, title, organization, publication year, category,
    summary, PDF URL). Enforces RLS permitting public reads for authenticated clinicians.

- database/migrations/003_rag.sql
  * Why Created: Vector database storage and semantic similarity search functions.
  * Use:
    1. Enables `pgvector` extension (`CREATE EXTENSION IF NOT EXISTS vector`).
    2. Creates `guideline_chunks` table with `embedding vector(384)`, chunk text,
       guideline foreign key, page number, and token count.
    3. Builds an IVFFlat or HNSW cosine similarity index (`vector_cosine_ops`).
    4. Implements PostgreSQL RPC function `match_guideline_chunks(...)` which computes
       cosine similarity, filters by threshold, and returns the top matching records.

- database/migrations/004_clinical_decisions.sql
  * Why Created: Medical-legal audit trail schema for decision support actions.
  * Use: Creates `clinical_decisions` table (patient_id, clinician_id, recommendation,
    decision status: `accepted` | `modified` | `rejected`, clinician notes, timestamps).
    Implements foreign key constraints, indexes, and audit-level RLS.

- database/migrations/005_fix_schema_compatibility.sql
  * Why Created: Non-destructive migration to align vector dimensions and schema sync.
  * Use: Guarantees 384-dimensional vector compatibility with `BAAI/bge-small-en-v1.5`,
    syncs table columns with backend Pydantic models, and updates RPC function signatures.

--------------------------------------------------------------------------------
3.2. Baseline Seed Data (database/seed/)
--------------------------------------------------------------------------------

- database/seed/verified_guidelines.sql
  * Why Created: Baseline dataset containing verified WHO and CDC clinical guidelines.
  * Use: Populates `guidelines` and `guideline_chunks` tables with pre-computed embeddings
    for immediate demonstration without running manual ingestion from scratch.
