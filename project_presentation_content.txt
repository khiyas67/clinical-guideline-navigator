1. PROJECT OVERVIEW
================================================================================

Project Title:
AI-Assistant for Dynamic Clinical Guideline Navigator

Problem Statement:
Clinical practice guidelines from premier international health authorities (such as NICE, KDIGO, AHA/ACC/HFSA, and CDC) represent the gold standard of evidence-based medicine. However, they are voluminous, complex, multi-hundred-page documents that are impossible to query rapidly during standard 15-minute consultations. Busy clinicians face immense cognitive load when cross-referencing multi-morbid conditions, resulting in delayed guideline adoption or risky reliance on commercial AI chatbots that hallucinate unverified medical advice. Generic AI models lack patient-specific clinical context (such as baseline eGFR, active medications, or allergies), cannot verify official guideline page numbers, and offer no audit trail for medical-legal accountability.

Proposed Solution:
An enterprise-grade, evidence-grounded Clinical Decision Support System (CDSS) pairing high-throughput Retrieval-Augmented Generation (RAG) over authoritative clinical practice guidelines with patient-specific contextualization, structured clinical guidance, and an immutable decision audit trail. The system couples a modern React 19 / TypeScript single-page application with a high-performance Python FastAPI microservice, Supabase PostgreSQL with 'pgvector' dense vector indexing (HNSW), local 384-dimensional BGE embeddings ('BAAI/bge-small-en-v1.5'), and Groq Cloud LPU acceleration ('qwen/qwen3.8-27b'). The system strictly enforces zero fabrication, parameter completeness, multi-specialty guideline navigation across all 8 canonical clinical categories, and an explicit human-in-the-loop clinical governance workflow (Accept / Modify with rationale / Reject).

Main Objectives:
1. High-Precision Semantic Retrieval: Index authoritative clinical guidelines using 384-dimensional dense sentence embeddings ('BAAI/bge-small-en-v1.5') and cosine similarity in PostgreSQL ('pgvector' with HNSW indexing).
2. Evidence Grounding & Clinical Safety: Constrain generative synthesis strictly to retrieved evidence chunks, enforcing conditional treatment recommendations based on verified clinical thresholds and explicitly flagging missing diagnostic values.
3. Patient-Specific Contextualization: Automatically ground clinical advice against the selected patient's active diagnoses, medications, allergies, and vitals without exposing Protected Health Information (PHI).
4. Multi-Specialty Guideline Expansion: Support multi-category classification across 8 canonical clinical domains (Nephrology, Pain Management, Endocrinology, Diabetes, Cardiovascular, Hypertension, Infectious Disease, General) with direct links to official PDFs.
5. Quality Control & Duplicate Prevention: Provide an automated PDF ingestion pipeline with cryptographic SHA-256 analysis, structural readability verification, clinical authenticity scoring, and edition detection.
6. Clinician Oversight & Auditability: Enforce a human-in-the-loop decision governance workflow where clinician actions (Accept / Modify / Reject) are permanently recorded in an immutable PostgreSQL audit trail.
7. Point-of-Care Accessibility & Export: Deliver sub-second retrieval latency, responsive mobile-ready interface, and formatted clinical consultation report generation (PDF and DOCX).

Target Users:
- General practitioners, resident physicians, and clinical specialists.
- Hospital medical officers, outpatient clinicians, and clinical pharmacists.
- Healthcare quality researchers evaluating evidence-based practice compliance.

Key Benefits:
- Rapid Point-of-Care Decision Support: Sub-second guideline retrieval (~0.69s) and grounded recommendation synthesis (< 1.5s total round trip).
- Hallucination Elimination: If indexed evidence is insufficient (similarity < 0.45), the system returns an explicit insufficiency advisory rather than inventing medical recommendations.
- Traceability & Provenance: Every recommendation displays the publishing authority, document title, section heading, exact PDF page number, similarity score, and direct working PDF link.
- Parameter Completeness Guard: Never recommends specific dosages without baseline clinical parameters (e.g., eGFR, ACR, potassium) and highlights missing tests.
- Medical-Legal Accountability: Append-only decision capture with timestamps, clinician IDs, and clinician rationales.

Scope of the Project:

Architecture Description:
The application follows an enterprise decoupled client-server microservices pattern with strict separation between user presentation, identity/access control, local embedding computation, vector database search, and high-speed LLM inference:

1. User / Clinician: Interacts with the secure single-page application via modern web browsers (desktop, tablet, mobile).
2. React 19 Frontend: Built with TypeScript, Vite, and Tailwind CSS. Manages UI state, route guarding, dynamic category suggestions, patient profile management, interactive EvidenceCards, and report generation modals.
3. Supabase Authentication & RLS: Manages user session tokens (JWT) and enforces PostgreSQL Row Level Security (RLS) so clinicians can only access their own patient records and decision logs.
4. FastAPI Backend (REST API): Handles query routing, query embedding generation, context assembly, guideline QC ingestion, and RAG pipeline orchestration on port 8000.
5. Query Router: Pre-classifies inputs via regular expressions and a 60+ medical keyword lexicon into greeting, out_of_scope, unclear, or healthcare.
6. Local Embedding Engine: Uses sentence-transformers with 'BAAI/bge-small-en-v1.5' (384 dimensions) to convert queries and guideline chunks into dense normalized vectors locally on the server.
7. Supabase pgvector: PostgreSQL database with the pgvector extension and an HNSW cosine distance index. Executes the 'match_guideline_chunks' RPC to fetch top-k relevant guideline passages.
8. Evidence Validator: Evaluates whether retrieved chunks exceed similarity thresholds (threshold >= 0.45) and satisfy evidence completeness.
9. Groq Cloud Inference Engine: Invokes high-speed 'qwen/qwen3.8-27b' with low temperature (0.1) and strict clinical grounding instructions.
10. Evidence Grounded Output: Returns synthesized clinical advice alongside exact guideline source cards citing authority, title, section, page number, similarity score, and direct PDF link.
11. Clinician Decision Workflow: Clinician reviews advice and records an Accept, Modify (with mandatory rationale), or Reject decision.
12. Audit Trail Persistence: The finalized decision and evidence snapshot are written to the 'clinical_decisions' table in Supabase.
13. Report Generation Engine: Generates downloadable clinical consultation summaries in PDF (ReportLab) or DOCX (python-docx) formats via '/api/reports/export'.

3. RAG ALGORITHM
================================================================================

Step-by-Step Retrieval-Augmented Generation Pipeline:

Step 1: Clinical Query Submission
The clinician inputs a clinical query (or selects a dynamic category suggestion) from the assistant interface. The request payload contains: question, optional patient_id, clinician_id, and category filter.

Step 2: Query Classification (Query Router)
Before generating embeddings or querying LLMs, the query is evaluated by 'classify_query()':
- If matched as 'greeting', 'out_of_scope', or 'unclear', the pipeline returns an immediate standard response with zero vector search and zero LLM cost.
- If classified as 'healthcare', it proceeds to vector retrieval.

Step 3: Patient Context Retrieval
If a 'patient_id' is supplied, the backend fetches non-identifying clinical variables: age, gender, diagnosed medical conditions, active medications, documented allergies, and medical history summary. Clinician authorization is strictly enforced under RLS.

Step 4: Query Vector Embedding
The query string is prepended with the official BGE retrieval instruction:
"Represent this sentence for searching relevant clinical passages: <query>"
If pertinent patient conditions (e.g., stage 3 CKD) are identified and not in the prompt, they enrich the retrieval query. The BAAI/bge-small-en-v1.5 model generates a 384-dimensional normalized vector locally.

Step 5: Vector Similarity Search
The vector is passed to the Supabase PostgreSQL RPC function 'match_guideline_chunks'. pgvector performs an HNSW-indexed cosine distance calculation:
similarity = 1 - (chunk_embedding <=> query_embedding)
Only chunks satisfying similarity >= 0.45 are retrieved (default top_k = 5).

Step 6: Relevant Guideline Retrieval & Deduplication
The database returns structured records containing: content, page_number, section_title, guideline_title, organization, source_url, pdf_url, and similarity score. Chunks are deduplicated by guideline ID and section to maximize evidence diversity.

Step 7: Evidence Sufficiency Evaluation
The backend checks if retrieved chunks satisfy the clinical relevance threshold:
- If no chunks pass the threshold, the pipeline returns a safe Insufficient Evidence advisory.
- If sufficient evidence is present, the pipeline formats the chunks into a numbered evidence block.

Step 8: Grounded Groq LLM Synthesis
The prompt combines the system prompt, patient context, and evidence chunks. Groq Cloud generates a grounded response formatted into the standardized 7-part clinical response structure.

Step 9: Provenance & Direct PDF Resolution
The backend formats each source chunk into a SourceItem with organization, title, section, page, similarity score, and working direct PDF URL.

Step 10: Clinical Decision Capture
The frontend renders the structured advice, displays interactive EvidenceCards, and surfaces Accept / Modify / Reject governance buttons. Actions are persisted directly into the immutable audit trail.

```python
def run_rag_pipeline(request: QueryRequest) -> QueryResponse:
    # 1. Intent Classification via Query Router
    q_type, canned_answer = classify_query(request.question)
    if q_type in ["greeting", "out_of_scope", "unclear"]:
        return QueryResponse(type=q_type, answer=canned_answer, sources=[])

    # 2. Retrieve Authorized Patient Context (if selected)
    patient_context = None
    if request.patient_id:
        patient_context = get_patient_clinical_context(
            patient_id=request.patient_id,
            clinician_id=request.clinician_id
        )

    # 3. Contextual Query Enrichment
    retrieval_query = request.question
    if patient_context and patient_context.get("conditions"):
        conds = [c for c in patient_context["conditions"] if c.lower() not in request.question.lower()]
        if conds:
            retrieval_query = f"{request.question} ({', '.join(conds[:2])})"

    # 4. Dense Vector Embedding (384 dimensions)
    query_vector = embed_query(retrieval_query)

    # 5. pgvector Cosine Similarity Retrieval (HNSW RPC)
    chunks = retrieve_guideline_chunks(
        query_embedding=query_vector,
        match_threshold=0.45,
        match_count=5
    )

    # 6. Sufficiency Verification
    if not chunks:
        return QueryResponse(
            type="healthcare",
            answer="I could not find sufficiently relevant evidence in the currently indexed clinical guidelines...",
            sources=[]
        )

    # 7. Grounded LLM Synthesis via Groq (qwen/qwen3.8-27b)
    answer = generate_grounded_answer(
        question=request.question,
        evidence_chunks=chunks,
        patient_context=patient_context
    )

    # 8. Source Formatting & Provenance Mapping
    sources = []
    for c in chunks:
        sources.append(SourceItem(
            guideline_id=str(c["guideline_id"]),
            title=c["guideline_title"],
            organization=c["organization"],
            section=c["section_title"],
            page=c["page_number"],
            excerpt=c["content"][:260] + "...",
            pdf_url=c["pdf_url"],
            similarity=round(float(c["similarity"]), 4)
        ))

    return QueryResponse(type="healthcare", answer=answer, sources=sources)
```

5. QUERY ROUTER ALGORITHM
================================================================================

Purpose:
A deterministic, rule-based pre-retrieval triage layer that classifies inputs to minimize latency, eliminate unnecessary LLM compute costs, and guard system boundaries.

Classification Categories:
1. Greeting:
   - Patterns: "hi", "hello", "good morning", "hey", "how are you"
   - Action: Returns immediate friendly clinical assistant greeting (0 vector search, 0 LLM cost).
2. Out-of-Scope:
   - Patterns: Sports, coding, entertainment, trivia, politics, non-clinical tasks.
   - Action: Returns polite boundary reminder that the system is dedicated to healthcare decision support.
3. Unclear:
   - Patterns: Very short strings (< 3 chars), random keystrokes ("asdf", "xyz").
   - Action: Prompts clinician to enter a specific medical question or select a patient.
4. Healthcare:
   - Patterns: Evaluated against a 60+ medical keyword lexicon (e.g., "hypertension", "diabetes", "sglt2", "egfr", "dosage", "pain", "stewardship", "covid", "contraindication").
   - Action: Routes to the full RAG pipeline for vector retrieval and grounded synthesis.

6. EMBEDDING & VECTOR SEARCH
================================================================================

Embedding Model:
- Model Name: 'BAAI/bge-small-en-v1.5' (Beijing Academy of Artificial Intelligence)
- Architecture: Transformer-based dense encoder running locally via sentence-transformers.
- Embedding Dimensionality: 384 dimensions (exact float values).
- Normalization: L2 unit-norm normalized, enabling cosine similarity via simple dot product.
- Instruction Prefix: Formatted as "Represent this sentence for searching relevant clinical passages: <text>"

Vector Search Implementation:
- Storage Engine: Supabase PostgreSQL 15+ with 'pgvector' extension.
- Table: 'public.guideline_chunks' with column 'embedding vector(384)'.
- Vector Index: HNSW (Hierarchical Navigable Small World) with 'vector_cosine_ops'.
- Distance Metric: Cosine distance operator (<=>).
  Similarity = 1 - (chunk.embedding <=> query_embedding)
- Stored Procedure: 'match_guideline_chunks' joins chunks with guidelines table to return rich metadata in a single sub-second database query (~0.69s latency).

8. GROQ / LLM GENERATION & CLINICAL SAFETY
================================================================================

Inference Engine:
- Provider: Groq Cloud LPU (Language Processing Unit) acceleration.
- Model: 'qwen/qwen3.8-27b' (High throughput, strong clinical reasoning, low hallucination).
- Temperature: 0.1 (Strict deterministic, evidence-bounded generation).

Clinical Safety Rules (Enforced in System Prompt):
1. Zero Fabrication & Strict Grounding: Rely ONLY on the provided retrieved guideline evidence chunks. Do NOT invent dosages, contraindications, or laboratory thresholds not present in evidence.
2. Parameter Completeness & Conditionality:
   - Never recommend specific medications or dosages without sufficient patient data and supporting evidence.
   - When required clinical parameters (e.g., eGFR, ACR, serum potassium, allergies, pregnancy status) are absent in the record, frame recommendations as strictly CONDITIONAL (e.g., "Contingent upon verifying baseline eGFR >= 20 mL/min/1.73m2 and serum potassium < 5.0 mEq/L...").
   - Rigorously distinguish established patient facts from clinical assumptions.
3. Secondary Source Segregation: If evidence originates from a supporting clinical reference (such as the Clinician Community Contributed SGLT2i Summary), clearly label it as secondary clinical guidance and NEVER present it as an official practice guideline.

Standardized 7-Part Response Format (When Patient Context is Present):
1. Clinical Summary: Concise 2-3 sentence overview directly addressing the clinical inquiry.
2. Relevant Patient Context: Bullet points summarizing pertinent patient parameters, diagnoses, and medications.
3. Clinical Assessment: Synthesis of how patient parameters align with guideline-directed therapy.
4. Evidence-Based Recommendations: Numbered, conditional clinical steps with specific drug classes and prerequisite criteria.
5. Safety Considerations & Monitoring: Cautions, contraindications, drug-drug interactions, renal adjustments, and monitoring intervals.
6. Missing Clinical Information & Recommended Tests: Explicitly lists diagnostic tests, baseline labs (eGFR, ACR, K+), or vitals needed before finalizing therapy.
7. Clinical Sources: Bulleted list of cited official guidelines with publishing authority, document title, section, page number, and direct PDF URL.

Fallback for General Inquiries (No Patient Selected):
When no patient context is selected, the response is explicitly titled:
"### General Clinical Guideline Advisory (No Patient Context Selected)"
with general summary, evidence-based guidance, monitoring considerations, and clinical sources.

10. CLINICAL GUIDELINE QUALITY CONTROL & INGESTION PIPELINE
================================================================================

To ensure that only authentic, uncorrupted clinical guidelines are added to the system, an enterprise QC pipeline was engineered in 'backend/app/services/guideline_qc.py':

Validation Stages:
1. Structural PDF Inspection: Verifies valid PDF magic bytes ('%PDF-'), readable digital text layers, and non-empty content (blocks corrupted or scanned image-only files lacking OCR).
2. Clinical Authenticity Scoring: Scans text against a 60+ item clinical practice lexicon (e.g., 'clinical practice guideline', 'recommendation', 'randomized controlled trial', 'pharmacotherapy', 'contraindication'). Rejects unrelated documents (invoices, recipes, source code, marketing).
3. Cryptographic SHA-256 Analysis: Computes file checksum and verifies against 'public.guideline_documents' to block exact duplicate uploads.
4. Auto-Category Detection: Automatically maps document content to the 8 canonical clinical categories.
5. Section-Aware Chunking: Chunks text into bounded windows (400-600 tokens with 50-token overlap), tracking physical page numbers and clinical section headings.
6. Batch Vector Embedding: Embeds chunks using 'BAAI/bge-small-en-v1.5' into 'vector(384)' and stores records in Supabase pgvector.

11. CLINICAL DECISION MANAGEMENT & AUDIT TRAIL
================================================================================

Workflow Overview:
To uphold the principle of human-in-the-loop clinical governance, every AI-assisted recommendation requires clinician review before it becomes part of the patient's record.

Decision Actions:
1. ACCEPT: Clinician approves the AI recommendation as clinically valid.
2. MODIFY: Clinician edits or customizes the guidance to reflect specific patient nuances or institutional policies. Clinician must provide a mandatory clinical rationale. Both original and modified text are stored.
3. REJECT: Clinician rejects the guidance and provides a clinical rejection rationale.

Audit Trail Table ('public.clinical_decisions'):
- id (UUID, Primary Key)
- clinician_id (UUID, References auth.users)
- patient_id (UUID, References public.patients)
- guideline_id (UUID, References public.guidelines)
- query_text (TEXT, Original clinical question asked)
- decision_text (TEXT, Final accepted or modified clinical plan)
- decision_status (TEXT, CHECK: 'accepted' | 'rejected' | 'modified')
- rationale (TEXT, Recorded clinician justification)
- modification_notes (TEXT, Specific edits made)
- evidence_sources (JSONB, Full snapshot of retrieved guideline chunks, titles, and pages)
- created_at (TIMESTAMPTZ, Immutable timestamp)

Medical-Legal Invariant:
The 'clinical_decisions' table has NO update or delete policies for authenticated users. Once recorded, clinical decisions cannot be altered or deleted, providing complete medical-legal defensibility.

20. ALGORITHM COMPLEXITY / PERFORMANCE
================================================================================

1. Query Router Classification:
   - Time Complexity: O(k) where k is the number of regular expressions and keyword dictionary items.
   - Latency: < 1 millisecond.
2. Local Dense Embedding Generation:
   - Time Complexity: O(N * d) where N is token sequence length (~30 tokens) and d = 384 dimensions.
   - Latency: ~25 milliseconds on standard CPU.
3. Vector Similarity Search (HNSW in pgvector):
   - Time Complexity: O(log M) search complexity in HNSW graph where M is total chunks (1,990).
   - Latency: ~10 milliseconds database RPC execution.
4. Groq Cloud LPU Generation:
   - Time Complexity: O(T) where T is generated token count (~350 tokens).
   - Latency: ~450 - 650 milliseconds.
5. Total End-to-End Latency:
   - Total Round Trip: < 1.0 second from clinician submit to fully rendered guidance.
