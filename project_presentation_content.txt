1. PROJECT OVERVIEW
================================================================================

Project Title:
AI-Assistant for Dynamic Clinical Guideline Navigator

Problem Statement:
Clinical practice guidelines from international health authorities (such as the WHO and CDC) are extensive, complex, multi-hundred-page documents that are difficult to query rapidly at the point of care. Busy clinicians often lack the time to manually search through voluminous documents, resulting in delayed guideline adoption or reliance on general-purpose AI tools that hallucinate unverified medical advice. Moreover, standard AI assistants lack patient-specific clinical context, cannot cite exact guideline page numbers, and offer no audit trail for medical-legal accountability.

Proposed Solution:
A specialized, evidence-grounded Clinical Decision Support System (CDSS) that pairs a modern React frontend with a FastAPI backend, pgvector semantic search over authoritative WHO and CDC clinical practice guidelines, and Groq high-throughput LLM synthesis. The system enforces strict evidence-grounding (zero extrapolation without retrieved evidence), incorporates individualized patient profiles (conditions, medications, allergies, history), provides direct citations to official PDF page numbers, and records a structured clinical decision audit trail (Accept / Modify / Reject).

Main Objectives:
1. High-Precision Retrieval: Index authoritative clinical practice guidelines using dense 384-dimensional sentence embeddings (BAAI/bge-small-en-v1.5) and cosine similarity in PostgreSQL (pgvector).
2. Evidence Grounding & Safety: Guard all AI responses using strict grounding prompts and a Query Router that bypasses RAG for greetings and out-of-scope inquiries.
3. Patient-Specific Contextualization: Automatically ground clinical guidance against active patient diagnoses, medications, and allergies without compromising PHI.
4. Clinician Oversight & Auditability: Provide an explicit Accept / Modify / Reject governance workflow where clinician decisions are persisted in an immutable audit trail with rationales.
5. Point-of-Care Accessibility: Deliver an intuitive, responsive interface with dynamic category suggestions and verified source links.

Target Users:
- General practitioners, resident physicians, and clinical specialists.
- Hospital medical officers and outpatient clinicians.
- Healthcare researchers evaluating evidence-based practice compliance.

Key Benefits:
- Rapid Point-of-Care Decision Support: Sub-second guideline retrieval and grounded recommendation synthesis.
- Hallucination Prevention: If indexed evidence is insufficient, the system explicitly returns an insufficient-evidence advisory rather than inventing medical recommendations.
- Traceability: Every recommendation displays the publishing authority, document title, section, page number, and similarity score.
- Accountability: Full clinician-in-the-loop decision capture for institutional review and patient safety.

Scope of the Project:
- Current Implemented Clinical Domains: Type 2 Diabetes Management (WHO HEARTS-D & 2nd/3rd line pharmacotherapy), Adult Hypertension (WHO Guideline), and Pain Management/Opioid Prescribing (CDC 2022 MMWR Guideline).
- Non-Scope / Boundaries: The system does NOT directly execute prescriptions, does NOT replace human clinical judgment, and explicitly restricts general non-medical queries.

2. SYSTEM ARCHITECTURE
================================================================================

Architecture Description:
The application follows a decoupled client-server microservices pattern with strict separation between user interface, authentication/persistence, embedding computation, vector retrieval, and LLM inference:

1. User / Clinician: Interacts with the secure single-page application via modern web browsers.
2. React 19 Frontend: Built with TypeScript, Vite, and Tailwind CSS. Manages UI state, route guarding, dynamic question suggestions, patient profile management, and interactive EvidenceCards.
3. Supabase Authentication & RLS: Manages user session tokens (JWT) and enforces PostgreSQL Row Level Security (RLS) so clinicians can only access their own patient records and decision logs.
4. FastAPI Backend (REST API): Handles query routing, query embedding generation, context assembly, and RAG pipeline orchestration on port 8000.
5. Query Router: Pre-classifies inputs via regular expressions and medical keyword dictionaries into greeting, out_of_scope, unclear, or healthcare.
6. Local Embedding Engine: Uses sentence-transformers with 'BAAI/bge-small-en-v1.5' (384 dimensions) to convert queries into dense normalized vectors locally on the server.
7. Supabase pgvector: PostgreSQL database with the pgvector extension and an HNSW cosine distance index. Executes the 'match_guideline_chunks' RPC to fetch top-k relevant guideline passages.
8. Evidence Validator: Evaluates whether retrieved chunks exceed similarity thresholds and satisfy evidence sufficiency.
9. Groq Cloud Inference Engine: Invokes high-speed Llama-3.3-70b-versatile with temperature=0.1 to generate grounded clinical advice.
10. Evidence Grounded Output: Returns synthesized clinical advice alongside exact guideline source cards (organization, title, page, similarity, and official PDF links).
11. Clinician Decision Workflow: Clinician reviews advice and records an Accept, Modify, or Reject decision with clinical rationale.
12. Audit Trail Persistence: The finalized decision and evidence snapshot are written to the 'clinical_decisions' table in Supabase.

3. RAG ALGORITHM
================================================================================

Step-by-Step Retrieval-Augmented Generation Pipeline:

Step 1: Clinical Query Submission
The clinician inputs a clinical query (or selects a dynamic category suggestion) from the assistant interface. The request payload contains: question, optional patient_id, and category.

Step 2: Query Classification (Query Router)
Before generating embeddings or querying LLMs, the query is evaluated by 'classify_query()':
- If matched as 'greeting', 'out_of_scope', or 'unclear', the pipeline returns an immediate standard response with zero vector search and zero LLM cost.
- If classified as 'healthcare', it proceeds to vector retrieval.

Step 3: Patient Context Retrieval
If a 'patient_id' is supplied, the backend fetches non-identifying clinical variables: age, gender, diagnosed medical conditions, active medications, documented allergies, and medical history summary.

Step 4: Query Vector Embedding
The query string is prepended with the BGE retrieval instruction:
"Represent this sentence for searching relevant clinical passages: <query>"
The BAAI/bge-small-en-v1.5 model generates a 384-dimensional normalized vector.

Step 5: Vector Similarity Search
The vector is passed to the Supabase PostgreSQL RPC function 'match_guideline_chunks'. pgvector performs an HNSW-indexed cosine distance calculation:
similarity = 1 - (chunk_embedding <=> query_embedding)
Only chunks satisfying similarity >= 0.40 are retrieved (default top_k = 5).

Step 6: Relevant Guideline Retrieval & Deduplication
The database returns structured records containing: content, page_number, section_title, guideline_title, organization, source_url, pdf_url, and similarity score.

Step 7: Evidence Sufficiency Check
If zero chunks pass the similarity threshold, the pipeline immediately returns:
"I couldn't find sufficiently relevant evidence in the currently indexed clinical guidelines to answer that question confidently..."
This prevents hallucination before LLM invocation.

Step 8: Prompt Construction
A strict prompt is synthesized containing:
- System Prompt: Defines Clinical Navigator's role, zero-extrapolation rule, explicit citation mandate, and insufficiency statement directive.
- Patient Context Section: Lists patient age, gender, conditions, allergies, and medications.
- Retrieved Guideline Evidence Section: Formats each evidence block with organization, guideline title, section, page number, and chunk text.
- User Question.

Step 9: Groq High-Speed LLM Generation
The prompt is transmitted to Groq cloud API utilizing 'llama-3.3-70b-versatile' (with automated fallback to candidate models if needed). Temperature is set to 0.1 to enforce deterministic, evidence-grounded outputs.

Step 10: Source Metadata Assembly
The backend compiles 'SourceItem' objects including guideline title, organization, section, page number, similarity percentage, clean text excerpt, and direct PDF URLs.

Step 11: Final Response Delivery
The frontend renders the structured recommendation, patient applicability badges, and interactive EvidenceCards.

Step 12: Decision Persistence & Audit Trail
When the clinician selects Accept, Modify, or Reject, the decision status, original AI answer, final modified decision, rationale, and snapshot of sources are saved to 'public.clinical_decisions'.

4. RAG PSEUDOCODE
================================================================================

ALGORITHM: ClinicalGuidelineRAGOrchestration
INPUT:     Question Q, Optional PatientID P_id, Optional Category C
OUTPUT:    Response Object (Type, Answer, Sources[])

BEGIN
    CleanedQuery = Trim(Q)
    
    // Step 1: Query Router Pre-Classification
    (QueryType, CannedResponse) = ClassifyQuery(CleanedQuery)
    
    IF QueryType IN ["greeting", "out_of_scope", "unclear"] THEN
        RETURN QueryResponse(type=QueryType, answer=CannedResponse, sources=[])
    END IF
    
    // Step 2: Patient Context Extraction
    PatientContext = NULL
    IF P_id IS NOT NULL THEN
        PatientContext = FetchPatientContext(P_id) // Age, Conditions, Allergies, Meds
    END IF
    
    // Step 3: Local Dense Vector Embedding
    PrefixedQuery = "Represent this sentence for searching relevant clinical passages: " + CleanedQuery
    QueryVector = BGE_Embed(PrefixedQuery, dimensions=384, normalize=TRUE)
    
    // Step 4: Vector Similarity Search via pgvector
    EvidenceChunks = Execute_RPC("match_guideline_chunks", {
        query_embedding: QueryVector,
        match_threshold: 0.40,
        match_count: 5
    })
    
    // Step 5: Evidence Sufficiency Verification
    IF Length(EvidenceChunks) == 0 THEN
        RETURN QueryResponse(
            type="healthcare",
            answer="The currently available indexed guideline evidence is insufficient to answer this specific question with confidence.",
            sources=[]
        )
    END IF
    
    // Step 6: Evidence & Context Prompt Construction
    FormattedEvidence = FormatEvidenceBlocks(EvidenceChunks) // Org, Title, Section, Page, Content
    FormattedPatient = FormatPatientProfile(PatientContext)
    
    PromptPayload = ConstructGroundedPrompt(
        SystemInstructions=SYSTEM_GROUNDING_RULES,
        PatientContext=FormattedPatient,
        Evidence=FormattedEvidence,
        Question=CleanedQuery
    )
    
    // Step 7: Deterministic LLM Inference
    GroundedAnswer = InvokeGroqLLM(
        model="llama-3.3-70b-versatile",
        temperature=0.1,
        max_tokens=1024,
        prompt=PromptPayload
    )
    
    // Step 8: Source Metadata Extraction
    SourceCards = ExtractSourceMetadata(EvidenceChunks)
    
    // Step 9: Return Grounded Response
    RETURN QueryResponse(
        type="healthcare",
        answer=GroundedAnswer,
        sources=SourceCards
    )
END

5. QUERY ROUTER ALGORITHM
================================================================================

Purpose:
Acts as a computational and safety gatekeeper. It classifies inbound queries prior to embedding generation or database querying, ensuring cost efficiency, fast response times for non-clinical interactions, and clear boundary enforcement.

Classification Classes & Behavior:

1. Greeting:
   - Detection: Regex matching for common salutations (e.g., "hi", "hello", "good morning", "who are you").
   - Action: Returns friendly introductory guidance without invoking vector search or LLM.
   - Response: "Hello! 👋 How can I help you with a healthcare or clinical guideline question today?"

2. Out-of-Scope:
   - Detection: Regex matching for programming code requests, sports results, movie trivia, jokes, financial queries, and general web questions.
   - Action: Returns boundary enforcement notice.
   - Response: "I'm designed to assist with healthcare and clinical guideline-related questions. Please ask me something related to a patient's condition, diagnosis, treatment, medication, or clinical guidelines."

3. Unclear:
   - Detection: Inputs that are empty, or <= 2 words with zero medical terminology.
   - Action: Prompts clinician for additional clinical specifics.
   - Response: "I couldn't quite understand your clinical question. Could you please provide more detail about the patient's condition, symptom, or the guideline topic you'd like to consult?"

4. Healthcare:
   - Detection: Matches extensive curated medical dictionary (diseases, drugs, diagnostics, guidelines, clinical actions) or multi-word clinical phrases.
   - Action: Routes to full RAG pipeline (BGE Embeddings -> pgvector -> Groq).

6. EMBEDDING & VECTOR SEARCH
================================================================================

Embedding Model:
- Model Identifier: BAAI/bge-small-en-v1.5
- Framework: sentence-transformers (PyTorch backend)
- Vector Dimensionality: 384 dimensions
- Normalization: L2 Normalized embeddings (enabling cosine similarity computation via dot product)
- Query Prefixing: Automatically prepends "Represent this sentence for searching relevant clinical passages: " to optimize retrieval performance for asymmetric search tasks.

Vector Database & pgvector Setup:
- Database Engine: PostgreSQL 15+ hosted on Supabase
- Extension: pgvector
- Column Type: VECTOR(384) on table 'public.guideline_chunks'
- Index Type: HNSW (Hierarchical Navigable Small World) index
- Index Definition: CREATE INDEX idx_guideline_chunks_embedding ON public.guideline_chunks USING hnsw (embedding vector_cosine_ops);
- Similarity Metric: Cosine Distance (<=> operator), converted to similarity via (1 - (embedding <=> query_embedding))
- Default Match Threshold: 0.40 (40% minimum cosine similarity)
- Default Top-K Retrieval: 5 chunks
- RPC Function: match_guideline_chunks(query_embedding, match_threshold, match_count, filter_guideline_id)

Evidence Grounding & Safety Rules:

2. Attribution Requirement: The model must cite the publishing health authority (WHO / CDC) when presenting recommendations.

   "The currently available indexed guideline evidence is insufficient to answer this specific question with confidence."
4. Patient Context Synthesis: Patient age, diagnosed conditions, active medications, and allergies are incorporated into the prompt, enabling the LLM to cross-reference guideline contraindications with patient-specific factors.

10. CLINICAL DECISION MANAGEMENT & AUDIT TRAIL
================================================================================

Workflow Overview:
To uphold the principle of human-in-the-loop clinical governance, every AI-assisted recommendation requires clinician review before it becomes part of the patient's record.

Decision Actions:
1. ACCEPT: Clinician approves the AI recommendation as clinically valid.
2. MODIFY: Clinician edits or customizes the guidance to reflect specific patient nuances or institutional policies. Both the original AI recommendation and the clinician's modified text are preserved.
3. REJECT: Clinician rejects the guidance and provides a mandatory or optional clinical rejection rationale (e.g., patient intolerance, acute contraindication).

11. SECURITY & AUTHENTICATION
================================================================================

Security Architecture:
- Authentication Provider: Supabase Auth (OAuth 2.0 / JWT session handling).
- Protected Routes: Frontend 'ProtectedRoute' wrapper intercepts unauthenticated requests and redirects to '/login'.
- Row Level Security (RLS): All PostgreSQL tables ('patients', 'clinical_decisions', 'guidelines') have RLS enabled:
  * 'patients': Clinicians can SELECT/INSERT/UPDATE/DELETE ONLY rows where 'clinician_id = auth.uid()'.
  * 'clinical_decisions': Clinicians can view and record decisions ONLY for patients they own.
  * 'guidelines' & 'guideline_chunks': Authenticated users have read-only SELECT permissions.
- Backend Secrets Protection: Groq API keys and Supabase Service Role keys reside strictly in server-side '.env' files and are never exposed to client browsers.
- No-Referrer Policy: Frontend external guideline links use 'referrerPolicy="no-referrer"' to prevent leaking internal application hostnames to third-party medical repositories.

14. IMPORTANT SOURCE CODE MODULES
================================================================================

1. MODULE: backend/app/services/query_router.py
   PURPOSE: Fast pre-retrieval query classifier that filters non-clinical traffic.
   INPUT:   Raw query string (e.g., "Hi", "What is first line for diabetes?").
   PROCESS: Tests query against regex patterns (greetings, trivia, coding) and a 60+ item medical keyword lexicon.
   OUTPUT:  Tuple of (ResponseType, CannedAnswerText). ResponseType is one of: 'greeting', 'out_of_scope', 'unclear', 'healthcare'.

2. MODULE: backend/app/services/embeddings.py
   PURPOSE: Computes dense vector embeddings locally using sentence-transformers.
   INPUT:   Clinical query text or batch of document chunk strings.
   PROCESS: Loads 'BAAI/bge-small-en-v1.5' as a thread-safe singleton, adds query instruction prefix, and normalizes output.
   OUTPUT:  384-dimensional list of floating-point numbers.

3. MODULE: backend/app/services/retrieval.py
   PURPOSE: Interacts with Supabase pgvector to retrieve top matching guideline chunks and patient context.
   INPUT:   Query embedding (List[float]), similarity threshold (float), match count (int).
   PROCESS: Calls PostgreSQL RPC function 'match_guideline_chunks' and queries 'patients' table for context.
   OUTPUT:  List of chunk dictionaries (content, page_number, section, guideline_title, organization, similarity).

4. MODULE: backend/app/services/rag.py
   PURPOSE: Main orchestration engine linking Router, Embeddings, pgvector, and Groq.
   INPUT:   QueryRequest (question, patient_id, category).
   PROCESS: Routes query -> fetches patient profile -> embeds question -> retrieves chunks -> verifies evidence sufficiency -> invokes Groq -> formats SourceItems.
   OUTPUT:  QueryResponse (type, answer, sources).

5. MODULE: backend/app/services/groq_service.py
   PURPOSE: Interfaces with Groq API for ultra-fast, deterministic grounded response generation.
   INPUT:   Question, EvidenceChunks, PatientContext.
   PROCESS: Formats evidence blocks, injects clinical grounding system prompt, and calls llama-3.3-70b-versatile with temp=0.1.
   OUTPUT:  Evidence-grounded clinical response string.

6. MODULE: backend/app/ingestion/index_guidelines.py
   PURPOSE: Autonomous pipeline to ingest official PDF guidelines into vector tables.
   INPUT:   Verified guideline records with 'pdf_url' in Supabase.
   PROCESS: Downloads PDF -> extracts pages -> chunks with sliding window -> embeds with BGE -> batch inserts chunks to pgvector.
   OUTPUT:  Ingestion summary stats (documents indexed, chunks created, embeddings stored).

7. MODULE: src/lib/decisions.ts
   PURPOSE: Frontend persistence client for the clinical decisions audit trail.
   INPUT:   Decision payload (patient_id, question, ai_answer, final_decision, decision_status, sources, rejection_reason).
   PROCESS: Authenticates active clinician and executes parameterized insert into 'clinical_decisions' in Supabase.
   OUTPUT:  Persisted ClinicalDecision record or error object.

8. MODULE: src/data/clinicalSuggestions.ts
   PURPOSE: Centralized dictionary of category-specific clinical question prompts.
   INPUT:   Category name (e.g., 'Diabetes', 'Hypertension', 'Medications').
   PROCESS: Resolves category key and returns curated clinical prompt list.
   OUTPUT:  Array of 4 targeted clinical question strings.

15. DATABASE DESIGN
================================================================================

Table 1: public.patients
- Purpose: Stores clinician-managed patient demographic and clinical profiles.
- Primary Key: id (UUID, default gen_random_uuid())
- Foreign Keys: clinician_id -> auth.users(id) ON DELETE CASCADE
- Key Columns: patient_code (TEXT), full_name (TEXT), date_of_birth (DATE), gender (TEXT), medical_conditions (TEXT[]), allergies (TEXT[]), medications (TEXT[]), medical_history (TEXT).
- Triggers: 'trigger_generate_patient_code' (auto-assigns P-YYYY-XXX), 'trigger_patients_updated_at'.
- RLS Policy: STRICT. Clinicians can only SELECT, INSERT, UPDATE, DELETE rows where clinician_id = auth.uid().

Table 2: public.guidelines
- Purpose: Verified clinical guideline catalog and source registry.
- Primary Key: id (UUID)
- Key Columns: title (TEXT), organization (TEXT), description (TEXT), category (TEXT), version (TEXT), publication_date (DATE), document_type (TEXT), source_url (TEXT), pdf_url (TEXT), is_verified (BOOLEAN).
- RLS Policy: Authenticated clinicians have SELECT permission. Writes restricted to administrative seed/migration scripts.

Table 3: public.guideline_documents
- Purpose: Tracks physical guideline document files, checksums, and ingestion status.
- Primary Key: id (UUID)
- Foreign Keys: guideline_id -> public.guidelines(id) ON DELETE CASCADE
- Key Columns: document_name (TEXT), checksum (TEXT), ingestion_status ('pending' | 'processing' | 'completed' | 'failed').
- Unique Constraint: (guideline_id, checksum).
- RLS Policy: Authenticated users can SELECT.

Table 4: public.guideline_chunks
- Purpose: Granular text chunks with associated 384-dimensional dense vector embeddings.
- Primary Key: id (UUID)
- Foreign Keys: document_id -> public.guideline_documents(id), guideline_id -> public.guidelines(id).
- Key Columns: chunk_index (INTEGER), content (TEXT), page_number (INTEGER), section_title (TEXT), source_url (TEXT), pdf_url (TEXT), embedding (VECTOR(384)).
- Vector Index: HNSW index using vector_cosine_ops ('idx_guideline_chunks_embedding').
- RLS Policy: Authenticated users can SELECT.

Table 5: public.clinical_decisions
- Purpose: Immutable audit log of all clinician interactions with AI recommendations.
- Primary Key: id (UUID)
- Foreign Keys: clinician_id -> auth.users(id), patient_id -> public.patients(id) ON DELETE CASCADE.
- Key Columns: question (TEXT), ai_answer (TEXT), final_decision (TEXT), decision_status ('accepted' | 'rejected' | 'modified'), category (TEXT), sources (JSONB), rejection_reason (TEXT), created_at (TIMESTAMPTZ).
- RLS Policy: STRICT. Clinicians can SELECT, INSERT, UPDATE, DELETE only their own decision records for their own patients.

16. GUIDELINE INGESTION ALGORITHM
================================================================================

How an Official Medical PDF Becomes Searchable:

Step 1: Guideline Discovery
The ingestion script queries Supabase 'guidelines' table for entries with 'is_verified = true' and a non-null 'pdf_url'.

Step 2: Resilient PDF Retrieval
The script fetches the PDF binary using stream requests with standard User-Agent headers, validates that the first 4 bytes match '%PDF', and generates a SHA-256 checksum.

Step 3: Ingestion Status Tracking
A document record is upserted into 'guideline_documents' with 'ingestion_status = processing'.

Step 4: Page-Preserving Text Extraction
Using 'pypdf', the document is read page by page. Each extracted string is tagged with its exact 1-indexed page number.

Step 5: Sliding-Window Semantic Chunking
Pages are segmented into chunks using chunk_size=1000 characters and chunk_overlap=150 characters. The chunker scans for sentence breaks ('. ') to prevent cutting words and detects section headers using regular expressions.

Step 6: Batch Neural Embedding Generation
Chunks are passed to 'BAAI/bge-small-en-v1.5' in batches of 32. The model outputs 384-dimensional normalized vector representations.

Step 7: Batch Insertion to pgvector
Chunks, metadata (page_number, section_title, source_url, pdf_url), and embeddings are written to 'public.guideline_chunks' in batches of 50.

Step 8: Completion Verification
The document status is updated to 'completed'. The HNSW index automatically incorporates the new vectors for immediate sub-second similarity search.

20. ALGORITHM COMPLEXITY / PERFORMANCE
================================================================================

Computational Performance Characteristics:

1. Query Router Classification:
   - Mechanism: Compiled regular expression matching and set-lookup over a hash set of medical keywords.
   - Time Complexity: O(N) where N is query character length.
   - Practical Latency: < 1 millisecond.

2. Local Query Embedding:
   - Mechanism: Forward pass of BAAI/bge-small-en-v1.5 transformer model (33M parameters).
   - Time Complexity: O(L) where L is tokenized sequence length.
   - Practical Latency: 15–35 milliseconds on standard CPU.

3. Vector Similarity Search (HNSW in pgvector):
   - Mechanism: Greedy graph traversal over Hierarchical Navigable Small World layers.
   - Time Complexity: O(log M) where M is the total number of indexed vector chunks.
   - Practical Latency: 5–15 milliseconds across 1,200+ vectors.

4. Groq Cloud LLM Generation:
   - Mechanism: LPU (Language Processing Unit) inference on Llama-3.3-70b.
   - Practical Latency: 300–800 milliseconds for complete clinical answer generation.

Total End-to-End Latency: Approximately 0.5 to 1.1 seconds for full grounded clinical synthesis.

22. LIMITATIONS
================================================================================

Real System Limitations (Academic Transparency):
1. Domain-Specific Guideline Coverage: The active knowledge base is currently concentrated in 4 primary guideline sets (WHO Diabetes, WHO Hypertension, CDC Opioids). Clinical questions outside these indexed domains will trigger the insufficient-evidence safeguard.
2. Static Knowledge Base Snapshots: Guidelines represent published versions and require periodic execution of the ingestion pipeline to index newly issued amendments or living guideline updates.
3. Dependence on Quality of Source PDFs: Text extraction fidelity relies on OCR/digital text formatting of official PDF publications.
4. Non-Autonomous Prescribing: The tool provides decision support and does not interface directly with electronic health record (EHR) order entry systems.
